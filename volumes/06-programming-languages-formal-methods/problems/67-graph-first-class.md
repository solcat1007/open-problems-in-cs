# #67 图作为一等数据结构的纯函数语言

**状态**：`OPEN`
**领域**：编程语言设计
**首次提出**：作为设计问题长期存在，具体提出者不明确 `[待核实]`（Erwig 2001 的归纳图工作与 Mokhov 2017 的代数图 API 是这条线最明确的两块基石）
**参与门槛**：需要长期工程积累

---

## 一句话概述

能否设计一门纯函数式语言（或库），让图（graph）像列表、树一样成为"一等公民"——不可变、可组合、可模式匹配——而仍然支持高效的图算法？

## 形式化陈述

本问题无法写成单个数学命题，这是**设计问题**的典型特征。它由一组设计目标共同构成，且这些目标之间存在已被观察到的张力：

1. **不可变性**：图的表示在纯函数式语义下没有破坏性更新（in-place update）；
2. **组合性**：图上的运算（如并、交、删点、删边）有代数律（如分配律、幂等律），且这些律可作为重写规则被编译器利用；
3. **效率**：在上述两条约束下，典型图算法（最短路、最大流、拓扑排序）不比命令式实现差过一个量级以上；
4. **一等性**：图字面量、模式匹配、推导式（comprehension）等语法支持达到列表现有的水平。

问题即：**这四条能否同时满足？** 注意这不是"能否证明"的问题，而是"能否造出来"的问题——答案的形式是语言或库的实现，而不是定理。

## 为什么困难

困难不在数学，而在**数据结构的表示张力**。列表之所以能成为一等公民，是因为它有自然的不变式递归结构（头 + 尾），函数式定义与高效实现天然一致。图没有这样的结构：

- **邻接矩阵**纯函数式下每次更新都要复制整个矩阵；
- **邻接表**的"删一个节点、收缩编号"操作在持久化（persistent）语义下难以廉价实现；
- 许多高效图算法（如 Dijkstra 的堆优化、Union-Find）的核心操作是**破坏性更新**，而持久化数据结构会把这些操作退化为复制或额外开销。

此外，"纯函数式图算法"的复杂性界往往是**渐近常数恶化**的：文献中已观察到一些算法在纯函数式实现中多出一个对数因子（具体哪些算法、哪些实现，属于经验观察 `[待核实]`）。这个张力没有已知的原理性证明说不可以消除，也没有已知的全面解决方案。

## 当前最好结果

| 方向 | 已知最好结果 | 出处 |
|---|---|---|
| 表示一：归纳图 | 用"节点 + 邻接上下文"的函数式表示，使图可解构、可模式匹配，图算法可用标准函数式风格写出 | Erwig, *Inductive graphs and functional graph algorithms*, JFP, 2001（FGL 库） |
| 表示二：代数图 API | 把图定义为一个代数结构的表达式，图的构造与变换按代数律重写 | Mokhov, *Algebraic Graphs with Edge Labels*, 2017（Haskell 的 Alga 库） |
| 表示三：边中心表示 | King 的工作围绕边的函数式图表示与算法 `[待核实]` | King，Haskell 图库相关工作 |
| 下界 | 无已知非平凡结果——没有人证明过"持久化表示下图算法必然变慢"的一般性定理 | — |

**要点**：三种表示各自解决了一部分设计目标，没有一个同时满足全部四条。这不是失败，而是设计问题的常态。

## 解法现状与可行攻击路径

### 已解决的部分

- **图可以纯函数式地表示并支持可读的算法书写**——这一点已被 FGL（Erwig 2001）在数十种图算法上示范，包括最短路、生成树、匹配等。这是真正解决了的子问题。
- **图的代数 API 可以按定律重写**——Alga（Mokhov 2017）证明了删点、并、交等运算满足一组代数律，并实现为 Haskell 库。这解决了"组合性"这一条。
- **部分算法在归纳表示下有干净的函数式推导**——FGL 的文献给出了与命令式版本复杂度相当（至多多项式因子内）的实现。注意"相当"是经验层面的说法，非逐算法证明。

### 可行的攻击路径

| 路径 | 核心手段 | 当前状态 | 卡点 |
|---|---|---|---|
| 归纳表示扩展 | 以 Erwig 的上下文分解为核心，扩充模式匹配与类型类支持 | FGL 已可用，被多个 Haskell 图库采纳 | 删点/重编号操作开销；大规模动态图不实用 |
| 代数 API 路线 | 图即表达式，靠代数律做融合与优化 | Alga 已支持带边标签的图 | 算法层面（如最短路）仍需下沉到具体表示，两套表示的衔接不自然 |
| 半持久化混合 | 允许受控的内部可变性（如 Haskell 的 ST 单子），对外保持纯接口 | 实践中广泛使用 | 破坏了"一等"的纯语义目标——这是妥协而非解决 |
| 新语言原语 | 设计带图原语的语言（图模式匹配、图推导式） | 无已知成熟的尝试 `[待核实]` | 语言设计成本高，缺乏社区推动 |

### 已堵死的路径

暂无已知的原理性排除结果。没有人证明"不可变 + 高效 + 一等"三者不可兼得；同样，也没有人给出构造。这是本册中典型的**无障碍也无方案**状态。

### 裁决

**`已有部分解`**

归纳图与代数 API 两个方案已覆盖部分设计目标且工程可用。剩余的卡点是具体的表示效率与语言级语法支持，属于可以继续推进的工程-设计混合问题，不是数学开放问题。

## 研究路线图

1. **库路线（已走通一半）**：从 FGL 到 Alga，Haskell 社区在持续演化图库。下一步是统一两套表示，或给出表示间的语义保持转换。
2. **性能路线**：为持久化图操作建立系统的实证比较（哪些算法在哪些表示下慢多少）。目前这类比较零散，没有公认的基准。
3. **语言路线**：把图模式匹配做进语言。这是最激进的路线，需要设计、实现、类型理论三方面工作。
4. **理论路线**：为"持久化数据结构上图算法的开销"建立下界模型（类似配额法 fine-grained 分析）。目前几乎空白。

## 关键文献

1. **Erwig, M.** *Inductive Graphs and Functional Graph Algorithms.* Journal of Functional Programming 11(5), 2001. — 归纳图表示的奠基工作，FGL 库的理论基础。
2. **Mokhov, A.** *Algebraic Graphs with Edge Labels.* 2017. — 代数图 API 路线，Alga 库的论文 `[待核实]`（该路线另有 Mokhov 等的 *Algebraic Graphs with Class*, Haskell Symposium 2017）。
3. **King, D.** Haskell 图库与边中心表示相关工作，具体文献 `[待核实]`。
4. **Pierce, B.** *Types and Programming Languages.* MIT Press, 2002. — 理解函数式数据结构类型化设计的标准教材。

## 常见误区

- **误区：这是纯理论问题。** 恰恰相反——它的问题形式是"能否造出来"。给不出实现的理论讨论没有价值。
- **误区：既然 Haskell 有图库，问题已经解决了。** 库的存在不等于四条设计目标同时满足。现有库都至少牺牲一条（通常是效率或纯度）。
- **误区：命令式语言里图很自然，所以函数式语言也能"自然地"装下图。** 命令式语言靠指针共享与破坏性更新，这两样在纯语义下恰好不可用。类比是误导性的。
- **误区：这是性能工程问题，与语言设计无关。** 表示选择决定了算法的可写性，反过来语法支持决定哪些表示可行。这是表示、语法、性能的耦合设计问题。
- **误区：应该给图一个"标准表示"。** 本问题的历史（矩阵、邻接表、归纳图、代数式）提示：不同应用需要不同表示，统一表示本身可能不是正确目标。

## 可运行实验

**`experiments/functional_graph_bench.py`** — 持久化与可变图表示的实测对比

用 Python 分别实现两种图表示：(a) 不可变字典/元组构成的持久化表示（每次"更新"返回新结构）；(b) 可变邻接表。在相同的图上执行一串删点 + 重跑 BFS 的操作序列，测量两者的运行时间与内存。

**能观察到什么**：持久化表示在"每次更新都复制"的策略下开销随图规模显著增长；配合结构共享（path copying）能压回一部分。你会具体看到**纯语义与效率之间的折中长什么样**。

**不能说明什么**：Python 的内存模型与真正的纯函数式运行时（Haskell/GHC）完全不同；测得的常数不能推广为任何一般性结论。它演示的是折中的**存在性**，不是折中的**量级**——后者需要真实的持久化运行时基准。
