# #72 分布式逻辑编程

**状态**：`OPEN`
**领域**：编程语言 / 并发与分布式系统
**首次提出**：作为语言家族的探索集中出现于 1980 年代（Shapiro 1989 对并发逻辑编程语言家族的总结）；"分布式"维度的系统性成熟方案至今缺失
**参与门槛**：可以立刻上手做实验

---

## 一句话概述

逻辑编程（声明式地"描述解的条件"而非"给出求解步骤"）能否自然地扩展到分布式系统——逻辑变量跨网络共享、推理跨节点协作，而不退化为消息传递上的手工编程？

## 形式化陈述

顺序逻辑编程（Prolog 风格）的理想是：程序员只写关系与约束，求解策略由系统负责。把它搬上分布式环境，需要：

1. **逻辑变量的分布式合一（unification）**：变量可以跨节点共享，一处绑定处处可见，且该过程不引入死锁或数据竞争语义；
2. **搜索的分布**：证明搜索（回溯、剪枝）跨节点分解，失败传播与回滚的语义被精确定义；
3. **容错语义**：节点失败时，"一个分布式推理过程处于什么状态"有明确定义（对应顺序情形的失败子句语义的分布式版本）；
4. **声明性保持**：程序的可观察行为不依赖调度顺序（或至少其依赖被语言语义明确约束）。

**问题即**：能否设计一个语言（及其语义），使 1–4 同时成立，并存在可用的实现？注意这是设计问题——判据是语言与实现的存在及其性质证明，不是数学猜想。

## 为什么困难

- **合一与通信的耦合**：逻辑变量共享意味着"绑定"是分布式一致事件。1980 年代的并发逻辑编程语言（Shapiro 1989 总结的家族：并发约束语言、流合一语言等）解决了**单机并发**下的大部分语义，但网络分区、延迟、节点失败把"绑定的可见性"变成分布式一致性问题——这不再是逻辑语义能独立处理的。
- **回溯的分布式代价**：顺序 Prolog 的回溯在分布式情形下要求跨节点撤销副作用与绑定，开销与语义都很棘手。多数系统选择了"不回溯"（commit 式语义），但那部分放弃了逻辑编程的搜索优势。
- **声明性 vs 调度的矛盾**：分布式系统中调度顺序影响可观察行为（消息到达顺序、分区），而逻辑编程的理想是行为与策略无关。这个张力是**设计层面的根本张力**，没有已知的同时满足两者的方案；它也不是可被定理"否定"的对象，因为可以不断权衡。
- 历史上该方向在 1980–90 年代曾活跃，此后研究重心转移；一些关键的历史文献较专门，本档案对具体系统能力的引用保持保守。

## 解法现状与可行攻击路径

### 已解决的部分

- **并发（单机）逻辑编程的语义已解决**：Shapiro 1989 总结的语言家族给出了流式合一、约束传播、commit 语义等一批稳定的语言设计，各自有明确语义。
- **协调模型已解决**：元组空间模型（Gelernter & Carriero 1992）证明"把协调从计算中分离"是可实现的编程抽象，被多种语言采纳。
- **actor 语义基础已解决**：Clinger 1981、Agha 1986 给出消息传递并发对象的操作语义。

### 可行的攻击路径

| 路径 | 核心手段 | 当前状态 | 卡点 |
|---|---|---|---|
| 元组空间路线 | 用共享元组空间承载逻辑变量与约束 | 单机/局域可用，有工程实现 | 元组空间本身成为单点与瓶颈；一致性与分区的矛盾 |
| 约束传播路线 | 把分布式求解视为约束传播网络 | 局部可行 | 全局一致性约束的传播需要共识类机制，代价高 |
| commit 语义路线 | 放弃分布式回溯，采用不可逆选择（guard + commit） | 与 Shapiro 家族语言一脉相承 | 失去搜索的声明性优势——这本身是权衡而非解决 |
| 现代基础设施复用 | 在现代分布式中间件（复制存储、共识协议）之上重建逻辑变量共享 | 无已知成熟的系统级尝试 `[待核实]` | 抽象层次错配：中间件提供的一致性粒度与合一的细粒度需求不匹配 |

### 已堵死的路径

暂无已知的原理性排除结果。注意不要把"分布式一致性有固有代价（如 CAP 权衡）"误当成"分布式逻辑编程不可能"——前者限制的是**具体一致性承诺**，后者从未被证明。

### 裁决

**`已有部分解`**

单机并发与协调模型两块地基已建成且有可用实现；缺的是把逻辑变量的共享语义与分布式容错语义接起来的系统。路径清楚（上表四条都在走或可走），卡点是具体的一致性/性能/语义权衡——这是可继续推进的设计问题。

## 研究路线图

1. **先把语义写清楚**：给"分布式逻辑变量"一个小型演算语义（参考 [#69 对象-空间演算的元理论](69-object-space-calculus.md) 的方法论），明确分区与失败下的绑定可见性规则。这是后续一切工作的前提。
2. **复用现代共识设施**：在复制存储之上实现试用型（tentative）合一绑定，测量声明性保持与延迟的折中。属于可立刻动手的实验路线。
3. **限定领域验证**：在规则引擎、知识图谱推理等"天然分布式 + 天然逻辑"的领域做试点，而非追求通用语言。
4. **历史文献考古**：1980–90 年代的并发逻辑编程文献中可能存在未被复用的设计（如分布式 Prolog 的早期尝试，具体文献 `[待核实]`），值得系统重读。

## 关键文献

1. **Shapiro, E.** *The family of concurrent logic programming languages.* ACM Computing Surveys 21(3), 1989. — 本问题最直接的历史基础：单机并发逻辑编程的全景。
2. **Gelernter, D., Carriero, N.** *Coordination languages and their significance.* CACM 35(2), 1992. — 协调与计算分离的宣言，元组空间路线的理论源头。
3. **Agha, G.** *Actors: A Model of Concurrent Computation in Distributed Systems.* MIT Press, 1986. — 消息传递并发对象的标准参考。
4. **Clinger, W.** *Foundations of Actor Semantics.* AI Memo 636, MIT, 1981. — actor 语义的数学基础。
5. **Apt, K. R.** *Principles of Constraint Programming.* Cambridge University Press. — 约束编程的标准教材，约束传播路线的基础。

## 常见误区

- **误区：分布式逻辑编程就是"Prolog + 网络"。** 网络引入的是语义级新现象（分区、部分失败、延迟），不是把解释器搬到多台机器那么简单。
- **误区：逻辑变量共享和消息传递是等价的。** 共享变量要求绑定对全部持有者即时可见且一致；消息传递没有这个承诺。两者是不同的编程抽象。
- **误区：CAP 定理证明了这个方向不可能。** CAP 限制的是具体一致性承诺的选择，不否定任何编程抽象的存在——把系统定理误读为语言设计的不可能性是本册最常见的错误模式。
- **误区：这个方向已经死了。** 更准确的说法是**研究重心转移**：声明式、数据驱动的分布式处理（如流式查询、以数据为中心的协调）在工业界以别的名字持续存在；语言级严格化仍是空白。
- **误区：必须先解决一致性才能动手。** commit 式语义与限定领域方案都允许在弱一致性下先做实验，验证声明性保持的程度。

## 可运行实验

**`experiments/distributed_logic_vars.py`** — 试用型分布式合一样机

用 Python 模拟一个 3 节点系统：每个节点持有逻辑变量副本，绑定通过模拟网络（可注入延迟、丢包、分区）同步。实现最简单的策略：绑定事件带序号广播，冲突时按"先到先得 + 冲突即失败"。测量：(a) 正常情况下的绑定收敛延迟；(b) 注入分区后绑定的可见性不一致窗口；(c) 失败子句的撤销是否跨节点传播。

**能观察到什么**：分区时不同节点看到不一致的绑定——你会直观看到"逻辑变量的分布式语义"为什么必须显式规定分区行为。

**不能说明什么**：模拟网络不等于真实网络；样机策略只是无数可能设计中的一种，其表现不能推广。它验证的是**问题的存在性**（分区下语义确实会出问题），不是任何设计的好坏。
