# #66 云量子计算基础设施

**状态**：`PARTIAL`
**领域**：量子计算（系统与基础设施）
**首次提出**：2016 年 IBM 通过云端开放真实量子处理器访问，是"云量子计算"作为公开服务的起点 `[待核实]`（具体上线日期未核对）
**参与门槛**：需要长期工程积累

---

## 一句话概述

通过云端远程访问真实量子处理器的模式已经建立并可用（这是已有部分解的部分）；开放的是基准标准的缺失、结果的可复现性、以及与经典计算基础设施的深度集成。

## 形式化陈述

本问题是工程与系统问题，难以写成数学命题，如实说明。它可分解为四个可检验的服务属性：

1. **可用性**：远程用户能否可靠地提交、排队、取回量子电路的执行结果。
2. **透明度**：设备参数（拓扑、错误率、校准时间）对用户公开到什么程度、可信到什么程度。
3. **可复现性**：同一电路在不同时间、不同设备上的结果能否达到统计一致。
4. **可集成性**：量子执行能否嵌入经典工作流（HPC 调度、数据管道）且延迟与成本可接受。

**现状**：第 1 条已基本解决；第 2、3、4 条开放。注意这些属性目前没有公认的量化验收标准——缺少标准本身就是问题的一部分。

## 为什么困难

1. **硬件漂移使"同一设备"不是同一设备。** 量子处理器需要周期性校准，参数逐日漂移；今天跑出的结果与上周的结果不保证统计一致。这是可复现性问题的物理根源，不会因软件改进消失。
2. **基准指标不统一。** 各厂商用各自的指标（量子体积等）自我报告，定义细节与可比性存疑 `[待核实]`；跨设备的公平比较没有公认协议。
3. **排队与延迟。** 真实 QPU 是稀缺共享资源，交互式 / 混合工作流（量子—经典交替循环）受网络往返与排队延迟支配，许多变分算法因此实际不可行。
4. **透明度与商业利益的冲突。** 完整的校准与错误率数据是竞争敏感信息；用户评估"我的电路在这台设备上能不能跑"所需的信息，厂商未必有动力完整提供。
5. **软件栈的快速演化。** SDK 与硬件接口频繁破坏性变更，长期研究代码的维护成本高。

## 当前最好结果

| 方向 | 已知最好结果 | 出处 |
|---|---|---|
| 远程访问 | 多家厂商提供云端真实 QPU 访问（IBM Quantum、Amazon Braket、Azure Quantum、Google 等，均为公开存在的事实，不涉性能数字） | 各厂商公开文档 `[待核实]`（具体清单以官网为准） |
| 软件生态 | 开源 SDK（Qiskit、Cirq 等）与本地模拟器成熟，事实性存在 | 各项目公开仓库 |
| 公开参数透明度 | 主流厂商公开拓扑、部分错误率与校准状态 | 各厂商公开文档 `[待核实]` |
| 统一基准 | 无公认的跨设备统一基准；量子体积等指标的定义与可比性存疑 | `[待核实]`（相关定义文献） |
| 混合工作流 | 延迟敏感的量子—经典循环在云端访问模式下未实用化 | 无已知非平凡结果 |

## 解法现状与可行攻击路径

### 已解决的部分

- **远程访问模式本身**：登录、提交电路、取回结果的完整链路已标准化到普通研究者可日常使用的程度，多家服务商并存。这使"上真机做实验"的门槛从"在实验室"降到了"有浏览器"——是本问题被标为 `PARTIAL` 而非 `OPEN` 的原因。
- **本地模拟器生态**：开源 SDK 的模拟器让绝大多数算法开发可以先离线完成，云端真机只做最终验证。

### 可行的攻击路径

| 路径 | 核心手段 | 当前状态 | 卡点 |
|---|---|---|---|
| 基准标准化 | 独立第三方基准套件、跨设备协议 | 学术界有倡议 `[待核实]` | 厂商配合度；指标定义本身的科学性 |
| 可复现性工程 | 校准快照、数据版本化、结果元数据归档 | 零散实践 | 硬件漂移的物理根源无法用软件消除 |
| 混合工作流集成 | 就地经典协处理、低延迟专用接口 | 商业上有初步产品 `[待核实]` | 排队与网络延迟；变分算法对延迟极敏感 |
| 透明度机制 | 强制公开错误率协议、统一报告格式 | 无公认方案 | 商业竞争利益 |
| 与经典 HPC 的融合 | 把 QPU 作为 HPC 调度器下的一种资源 | 试验性项目 `[待核实]` | 两侧运维文化、编程模型差异大 |

### 已堵死的路径

暂无已知的原理性排除结果。唯一需要记录的**物理约束**（非障碍）：量子态不可克隆意味着云端基础设施无法对传输中的量子态做缓存与重传——量子资源与经典资源在基础设施层的抽象不可能完全同构。这约束设计，不排除可行性。

### 裁决

**`已有部分解`**

远程访问与软件生态已实质可用，且多家服务商的并存提供了基本的多样性；但基准、可复现性、透明度与深度集成四项均无公认解决方案，且部分卡点（硬件漂移、商业利益）不在软件层。

## 研究路线图

1. **短期（用户侧可做）**：建立自己的跨设备基准脚本与元数据记录习惯，把可复现性责任部分前置到实验设计——这是个人研究者唯一能立刻推进的方向。
2. **中期（社区侧）**：独立基准套件与跨设备报告协议的采纳——需要学术界与厂商的持续博弈。
3. **中期（工程侧）**：低延迟混合工作流接口，决定变分类算法在云模式下是否实用——与 [#60](60-nisq-to-ftqc.md) 的过渡路线耦合。
4. **长期（系统侧）**：QPU 纳入统一 HPC 资源调度——依赖前面各项的成熟。

## 常见误区

- **误区：云上跑通的实验说明量子计算"已经实用"。** —— 云访问解决的是**可得性**，不是**能力**；在云端设备上跑通小电路与 [#63](63-quantum-advantage.md) 的"实用优势"之间没有任何蕴含关系。
- **误区：厂商公布的指标可以直接横向比较。** —— 各家指标的定义、测量协议、更新频率不同；量子体积等指标的可比性本身存疑 `[待核实]`。跨设备结论必须自测。
- **误区：云端结果可以像经典计算一样复现。** —— 硬件漂移与校准周期使"同设备同电路"的结果随时间变化；可复现性需要显式的统计协议，而不是假设成立。
- **误区：排队延迟是小摩擦。** —— 对需要量子—经典快速交替的变分算法，云端往返延迟足以使其不可行；基础设施的延迟特性会**反向淘汰**某些算法路线。
- **误区：基础设施问题是纯软件问题。** —— 硬件漂移的物理根源、校准数据的商业敏感性都不在软件层；见 [#61](61-qubit-error-rate.md) 与 [#62](62-superconducting-scaling.md)。

## 可运行实验

**`experiments/transpilation_overhead.py`** — 本地模拟编译与映射开销

用开源 SDK 在本地模拟器上对同一量子电路分别映射到"全连接"与"近邻网格"两种虚拟拓扑，测量转译后电路深度、门数与两比特门数的膨胀；再用简单去极化噪声模型估算两种映射下的输出保真度差异。**能观察到**：连接性受限时编译开销显著——这是评估云端设备（拓扑各异）适配自家算法时应当做的第一步功课，也是 [#88 量子软件工程](../09-software-engineering/problems/88-quantum-software-engineering.md) 中编译器工作最小化的一例。

**绝不能说明**：本地噪声模型与真实设备的噪声（漂移、串扰、相关错误）不同，模拟结果**不能**预测云端真机上的实际表现；本实验也不测量任何真实云服务的延迟、队列与费用——那些只能实测，且随时间变化。
